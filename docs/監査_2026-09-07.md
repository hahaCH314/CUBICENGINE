# 監査 2026-09-07 — NeoForge 対応まわりの4件

`feature/neoforge-ready` の作業ツリー（GeckoLib のクラス分離、Forge 版
`LogicInterpreter` の `for` 復活、NeoForge の `ready: true`、リビルドした jar 2つ）を
監査した結果と、その場で直したもの。**4件すべて直してある。**

---

## 通っていたところ（直す必要が無かった）

- **`hasGeoMobs` ＋ `GeoSupport` の分離は正しい。** `ModEventHandler` は guard を
  通らない限り `CubicGeoEntity` を解決せず、`GeoSupport` は最初の `invokestatic` まで
  linking されない。旗はエンティティが湧く前に立ち、エクスポータの `useGeo` と
  完全に一致する（`toCubicData.ts` は `useGeo` のときだけ `render:"geo"` を出す）ので、
  旗と `geckolib` 依存行がズレることはない。
- **`LogicInterpreter.java` は HEAD 時点で本当にコンパイル不能だった**（`{` が38、`}` が39）。
  追加された `for (JsonObject rule : rules)` で直っている。neo 側には元から入っていた。
- **エクスポータが `neoforge.mods.toml` に `mandatory=true` を書いていた件は無害。**
  NeoForge の `ModInfo.ModVersion`（FML 4.0.43）は `type` の既定が `REQUIRED` で
  未知キーを無視する。ただし「たまたま」なので `type="required"` に直した（下の①）。
- 1.21.1 の `@EventBusSubscriber` に `bus` が要らないのも正しい。

---

## ① デスクトップ版が NeoForge を選んでも Forge の mod を作っていた

**症状。** `targets.ts` で NeoForge を選べるようにしたのに、デスクトップの
ビルド経路（`SettingsPanel` / `page.tsx` / `LaunchPanel` / `GrapePanel` の4つ）は
すべて `exporter.ts` の `buildJavaZip` を通り、そこが **Forge 1.20.1 の MDK 決め打ちで
`state.javaTarget` を一切見ていなかった**。NeoForge を選んだ人に Forge 1.20.1 の jar を
`mods` へ入れ、「Forge 1.20.1 で起動して確認してね」と案内していた。
Web 側の catch フォールバック（ソースZIP）も同じ穴。

**直し方。** `buildJavaZip` を出し先対応にした。**注入方式（完成済み .jar）とは別経路**で、
遊ぶ人の PC で gradle がコンパイルするので、要る値がまるごと違う。

出し先ごとに変わるもの（`lib/javaEngine/targets.ts` の `loader` / `mdk` に集約）:

| | Forge 1.20.1 | NeoForge 1.21.1 |
|---|---|---|
| gradle プラグイン | ForgeGradle 6 | ModDevGradle 2.0.144 |
| JDK | 17 | **21** |
| Gradle 本体 | 8.8 | **9.2.1**（8.8 では ModDevGradle が動かない） |
| 設定ファイル | `META-INF/mods.toml` | `META-INF/neoforge.mods.toml` |
| 依存の必須指定 | `mandatory=true` | `type="required"` |
| pack_format | 15 | 34 |

⚠️ `gradle-wrapper.properties` は同梱 base64（`lib/gradleWrapper.ts`）から外した。
あれは「Gradle 本体のどの版を落とすか」を書くファイルで、8.8 固定だった。
`gradlew` と `gradle-wrapper.jar` は本体を落として起動するだけなので版に依らず使い回せる。

⚠️ NeoForge の `settings.gradle` には foojay-resolver を入れてある。
遊ぶ人が JDK 21 を持っていなくても gradle が勝手に取ってくる。
無いと「JDK が見つからない」で止まり、子どもには原因が分からない。

**Java ソースの方言**は `lib/codegenJava.ts` の `DIALECTS` に1か所へ集めた。
**ここ以外に `net.minecraftforge` / `net.neoforged` を書かないこと。**
対応は推測ではなく `generic_engine_neo`（実際にコンパイルが通っているエンジン本体）から写した:

| Forge 1.20.1 | NeoForge 1.21.1 |
|---|---|
| `net.minecraftforge.eventbus.api.SubscribeEvent` | `net.neoforged.bus.api.SubscribeEvent` |
| `@Mod.EventBusSubscriber(...)` | `@EventBusSubscriber(...)` |
| `TickEvent.ServerTickEvent` ＋ `phase` 判定 | `ServerTickEvent.Post`（Pre/Post が別クラス） |
| `ServerLifecycleHooks.getCurrentServer()` | `event.getServer()` |
| `LivingHurtEvent` | `LivingDamageEvent.**Pre**` |
| `ForgeRegistries.ITEMS` / `.BLOCKS` | `BuiltInRegistries.ITEM` / `.BLOCK` |
| `getOrCreatePlayerScore(名前, o).getScore()` | `getOrCreatePlayerScore(p, o).get()` |
| `RegistryObject<T>` | `DeferredHolder<T, T>` |
| コンストラクタでバスを自分で取る | **バスが引数で渡ってくる** |

⚠️ `LivingDamageEvent` は **`Post` ではなく `Pre`**。Forge の `LivingHurtEvent` は
体力が減る**前**に鳴る。`Post` にすると「体力が n 以下なら」が減った後の値で判定され、
**同じ作品が Forge と NeoForge で違う動きをする**（遊んだ人しか気づけない）。

⚠️ NeoForge のメインクラスで `NeoForge.EVENT_BUS.register(this)` は**書いてはいけない**。
`@SubscribeEvent` メソッドが1つも無いクラスを渡すと NeoForge のバスは
`IllegalArgumentException` を投げ、MOD 読み込みごと失敗する（Forge は黙って無視していた）。

### 確かめたこと

- 生成した **NeoForge プロジェクトを実際に `gradlew build` して BUILD SUCCESSFUL**、
  `build/libs/project-1.0.0.jar` まで出た。きっかけは7種類すべて入れて確認
  （参加 / こわす / つかう / 毎ティック / チャット / ダメージ / おく）。
- Forge 側も同じく **BUILD SUCCESSFUL**。さらに**変更前のコードが出す生成物と差分を取り**、
  違いは README の文言1行と import の並び順だけ（＝Java 的に無意味）であることを確認した。
- `gradle-wrapper.properties` は変更前の base64 と**バイト単位で一致**。

**⚠️ ただしマイクラでの実機確認はしていない。** 確かめたのはコンパイルが通るところまで。
NeoForge 版を配る前に、伊波さんが実機で1回通すこと。

## ② 新しいエンジンが Service Worker のキャッシュに落ちていた

`public/sw.js` の `ALWAYS_FRESH` が `/base-mod.jar` しか挙げていなかったので、
`/base-mod-neo.jar` は stale-while-revalidate 扱いだった。
**SW が先に応答するので、exporter の `cache:"no-cache"` はそもそもネットワークまで届かない。**
`ALWAYS_FRESH` がまさに防ぐために存在する「古いエンジン／SPEC 不一致」事故そのもの。

→ `ALWAYS_FRESH` に追加し、`CACHE_NAME` を **v6** へ上げた（焼き付いた古い分を一掃するため）。

## ③ 同じ穴が HTTP ヘッダ側にもあった

`next.config.ts` の `Cache-Control: no-cache, must-revalidate` の対象も
`/base-mod.jar` だけだった。

→ 出し先の表（`JAVA_TARGET_LIST`）から作るようにした。**行を1つ足せば自動で付いてくる。**
`next build` の `routes-manifest.json` で両方に付くことを確認済み。

## ④ `GeoSupport` の約束が、書かれていない前提に頼っていた

`GeoSupport.java` は「GeckoLib のクラスはここ以外に出てはいけない」と書いてあるのに、
`cubicenginegenericMod` の `registerAttributes` と `registerRenderers` が
`CubicGeoEntity` / `CubicGeoRenderer` に触れていた。守っていたのは
**「ENTITIES は空」という書かれていない前提だけ**。geo でない `EntityType` を1つ
登録した瞬間に、`GeoSupport.java` を書いた理由の事故（起動時 `NoClassDefFoundError`）が
そのまま戻る形だった。

→ 両エンジンの2か所（計4か所）の先頭に `if (!DynamicRegistry.hasGeoMobs) return;` を入れ、
`GeoSupport` の説明を「許してある場所は次の3つ」と実態に合わせた。
jar を再ビルドし、**4か所すべて `getstatic hasGeoMobs` → `ifne` → `return` が
バイトコードに入っていることを javap で確認**。`npm run check:modid` も通っている。

## 触るときの注意（増えた分）

**出し先（ローダー／マイクラの版）を1つ増やすとき、必ず通る場所:**

1. `lib/javaEngine/targets.ts` に行を足す（`loader` と `mdk` も忘れずに）
2. `public/sw.js` の `ALWAYS_FRESH` に新しいエンジンの URL を足す
3. `lib/codegenJava.ts` の `DIALECTS` に方言を足す（**新しいローダーなら**）
4. `app/editor/exporter.ts` の `buildJavaZip` の分岐を通す（**新しいローダーなら**）

`next.config.ts` の Cache-Control と、画面の案内文（「〇〇 で起動して確認してね」「JDK 〇〇 が必要」）は
**表から作るようにしたので、もう足さなくてよい。**

# ヒマワリへ — Web から .jar が出るところまで来ました

2026-08-23、Windows 側のシオンより。

`base-mod.jar` 受け取りました。**ビルド成功しています。**
TS 側と繋いで、ブラウザで注入した `.jar` が生成されるところまで確認できました。

---

## 1. 動作確認（実測）

本物の `exportJava` を動かして、出てきた `.jar` を検証しました。

```
生成サイズ      : 17,775 bytes
.class          : 4個そのまま残存（＝壊していない）
mods.toml modId : .class の値と一致
設計図の場所    : assets/<modId>/cubic_data.json
中身            : rules 1件 / blocks 1件（id=magicstone, light=12, hardness=2.5）
```

**方式は成立しました。** ここまでは間違いありません。

---

## 2. 1点だけ変更しました：modId は固定に

あなたの実装は `.class` のバイナリ置換で modId を可変にしていました。
**技術的には正しく動きます。** 定数プールの長さ30を `padEnd` で保っていて、
クラスファイルが壊れないことも確認しました。実装として綺麗でした。

ただ、伊波さんの判断で **固定（選択肢A）** に戻しました。

> MODフォルダがぐちゃぐちゃになるから A。
> そもそも Java の需要は大人。

作るたびに別MODが増えると `mods` が散らかる。Java版の利用者は主に大人なので、
**作品を入れ替えて遊ぶ**ほうが扱いやすい、という理由です。

置換処理は外し、`ENGINE_MOD_ID` を `.class` に焼かれている
`cubic_xxxxxxxxxxxxxxxxxxxxxxxx`（30文字）に合わせました。

⚠️ もし今後エンジンを再ビルドして別の modId にするときは、
`lib/javaEngine/spec.ts` の `ENGINE_MOD_ID` も**同時に**直してください。
1文字違うだけで、MODは起動するのに何も動きません。

---

## 3. ブロック/アイテムもフル出力にしました

「登録タイミングは気にしなくていい」という回答、助かりました。
`toCubicData` を拡張し、モデルタブの `registered: true` のものを
`blocks` / `items` に出すようにしています。

```json
"blocks": [
  { "id": "magicstone", "displayName": "魔法の石", "hardness": 2.5, "lightLevel": 12 }
]
```

- `id` は `exporter.ts` の `sanitizeBlockName` と同じ規則で作っています
- `lightLevel` は 0〜15 に丸めています（16以上はマイクラが受け付けないため）
- `items` の `maxStack` は今 64 固定です。可変にしたいなら言ってください

---

## 4. お願いしたいこと：実機での確認

**`.jar` の形は正しいですが、中身が期待どおり動くかは未確認です。**
Forge 1.20.1 で起動しないと分かりません。

そちらにビルド環境があるので、確認してもらえると早いです。

### 見てほしいところ

| 確認したいこと | 期待 |
|---|---|
| MODが読み込まれるか | mods 一覧に出る |
| `cubic_data.json` を読めているか | ログに何か出る |
| rules が動くか | ワールドに入ったらメッセージが出る |
| blocks が登録されるか | クリエイティブに `magicstone` が出る |

### もし動かなかったとき

**マイクラは何も言わずに黙ります。** それがこの方式で一番怖いところです。

- `spec` の値が合わないときは、チャットかログに何か出す
- 知らない `type` が来たときも、握りつぶさず何か出す

そこさえ入っていれば、原因を追えます。
